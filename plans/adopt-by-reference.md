# Adopt by reference: one slate taking on another slate's positions

`plans/adopt-by-reference.md`

## Goal

Let a slate say "we hold these positions of that other slate" without copying
them, so republished picks aren't duplicated. Real cases from the public
endorsements catalog (`plans/openslate-public-endorsements.md`):

- California Professional Firefighters republishes the IAFF's US House picks.
- SFPOA and SF Firefighters Local 798 issued one joint statement (two bundles,
  identical positions).
- County parties repost the state party's statewide picks (Ventura Dems →
  CADEM; Alameda County GOP → CAGOP template; LA GOP "CAGOP" badges).
- Sierra Club chapters repost Sierra Club California's statewide and prop picks.

User direction (2026-10-19): "leaning towards an adopt by reference. but tool
should make it easy for publishers to pick their preferred method". So the
format gains adopt-by-reference, and the tooling offers the methods side by
side: **copy** the positions, **reference** them (live link), or **reference
with an embedded snapshot**.

## Decisions already made (don't re-ask)

1. Adopt by reference is the mechanism (user, 2026-10-19). Not a slate-level
   co-signer list, not per-position co-signer lists.
2. Tooling must let a publisher choose copy, reference, or reference+snapshot
   (user, 2026-10-19).
3. Within v1, as an optional field, with a §10.1 changelog entry (same
   precedent as `attribution`, 2026-05-31).
4. In the catalog, while adopts isn't supported end to end, republished picks
   are NOT copied. They're listed under `## Republished from <org>` in each
   bundle's NOTES.md for migration (catalog plan, round 2b).

## Design (SPEC §3.10 `Adoption`)

New optional `SlatePayload.adopts: Adoption[]`.

| Field | Type | Req | Notes |
| --- | --- | --- | --- |
| `issuer` | string | yes | Key that signed the adopted slate. |
| `of` | string | no | If the adopted slate is secondhand, its `attribution.of.name` (one researcher key signs many slates). |
| `election` | string | no | The adopted slate's `context.election`, to tell apart one entity's slates for different elections. |
| `uri` | string (URL) | one of | Where the adopted slate can be fetched (live: may be re-issued). |
| `slate` | string | one of | Embedded token: a snapshot that verifies offline. |
| `subjects` | Subject[] | no | Which positions to adopt, matched by subject identity (`id`, else title+jurisdiction+election). Absent = all. |
| `source` | string (URL) | no | Where the adopting entity published the adoption (evidence). |
| `note` | string | no | Free text. |

At least one of `uri` or `slate` is required.

Semantics:
- The adopting slate's entity (its `attribution.of` if secondhand, else its
  issuer) is claimed to hold the selected positions (stance, choice, weight) of
  the adopted slate. Statements and per-position sources stay the original's.
- A consumer resolves an adoption only from a slate that verifies, is issued
  by `issuer`, and matches `of`/`election` when given. If `slate` is embedded,
  use it; otherwise use a matching slate it already has, or fetch `uri`.
- Positions the adopting slate states itself win over adopted positions on the
  same subject.
- Adopted slates may themselves adopt. Resolve transitively up to depth 4, and
  ignore cycles.
- An unresolved adoption MUST NOT produce positions. Consumers SHOULD show it
  as "adopts N positions from <of> (not loaded)".
- Like `Reference`, an adoption is a claim by the adopting slate's signer.

Core API (shared by CLI and web):
- `subjectIdentity(subject)`: the collation key (same as web `subjectKey`).
- `slateEntity(payload)`: `{ key, name, secondhand }`.
- `adoptionMatches(adoption, payload)`.
- `resolveAdoptions(payload, find, { maxDepth })`: `find` returns candidate
  tokens for an adoption (sync). Returns adopted positions with their provenance
  chain, plus unresolved adoptions.

CLI:
- `sign` accepts `adopts` in the input JSON (passes through, schema-checked).
- `verify` lists adoptions, and resolves embedded ones.
- New `adopt <slate-file|url> --mode copy|reference|embed [--subjects <file>]
  [--source <url>] [--into <positions.json>]`. `copy` appends the positions,
  `reference` writes an `adopts` entry with `uri`, and `embed` adds the token.

## Findings / gotchas

- `vectors:generate` writes LF; this checkout is CRLF. The regenerated vector files show as modified but have no content change; `git add` normalizes them (no diff staged).
- Biome on this checkout needs `--line-ending=crlf` (ISSUES: "biome lint fails on CRLF checkouts"; ui/two-modes carries a config fix).

- The current master web app's Collate labels entries with `issuer.name`, so
  every catalog slate shows as "OpenSlate Public Endorsements". `ui/two-modes`
  fixes this (source = `attribution.of`). Don't fix it again on master.
- Closed schema: shipping slates with `adopts` before openslate.us has the new
  core makes those slates fail verification for every visitor.
